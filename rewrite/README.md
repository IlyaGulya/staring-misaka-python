# Staring Misaka — Bun / Effect 4 / grammY

Новая реализация в отдельном каталоге и отдельной SQLite-базе. Python-приложение и его миграции не изменяются. Production автоматически не переключается.

## Стек и границы

- Bun **1.4.2**, Effect **4.0.5**, `@effect/ai-anthropic` **4.0.5**, grammY **1.46.0**; точные зависимости в `package.json` и `bun.lock`. Effect AI API помечен `unstable`, поэтому обновления версий требуют контрактной проверки.
- Один процесс, `bun:sqlite`, WAL/FULL, короткие транзакции без сетевых `await`.
- Effect управляет конкурентностью, отменой, ресурсами и OTLP-трассировкой. grammY исполняет Bot API. GramJS — только наблюдение через отдельную пользовательскую MTProto-сессию.
- Классификатор использует нативный `effect/ai` и официальный `@effect/ai-anthropic`, обращаясь **напрямую к Anthropic Messages API** через `ANTHROPIC_API_KEY`. Не OpenRouter, не Codex-подписка. `LanguageModel.generateObject` получает единственную Effect Schema отчёта; модель не получает инструменты Telegram.
- Модель и промпты берутся из существующего `../config.yaml`; `LLM_MODEL` переопределяет модель только если непустой. Изменения промпта отражаются в `promptVersion`.

## Организация кода

| Где | Ответственность |
|---|---|
| `src/main.ts`, `application.ts` | CLI и сборка одного scoped runtime; владение SQLite и process lock |
| `src/runtime/` | Общий ingress двух transport-источников, worker loops и безопасная диагностика |
| `src/engine.ts` | Ограниченный batch: claim → I/O → conditional commit; finalizer сохраняет прерванную попытку |
| `src/store.ts` | Публичная граница коротких синхронных транзакций |
| `src/storage/ingestion.ts`, `classification.ts`, `actions.ts` | Раздельные переходы входящих событий, классификации и модерации/отмены |
| `src/storage/database.ts`, `records.ts`, `codecs.ts` | SQLite schema v1, точные типы SQL-выборок и проверка persisted JSON |
| `src/storage/administration.ts`, `queries.ts`, `legacy.ts`, `journal.ts` | Управление, диагностика, импорт и экспорт аудита |
| `src/classifier.ts`, `classification/` | `SpamClassifier`: проверяемое правило → bounded evidence → Effect AI → доменная проверка verdict |
| `src/telegram.ts`, `telegram-observations.ts` | Bot API transport отдельно от нормализации входа |
| `src/observer.ts`, `observer-observations.ts`, `media.ts` | Жизненный цикл MTProto отдельно от нормализации и хранения изображений |
| `src/commands.ts`, `domain.ts`, `notifications.ts` | Типизированные команды и авторизация; общие контракты; единый текст для receipt reconciliation |

`Store` владеет транзакциями; внутренние storage workflows не коммитят отдельные куски принятого batch. Сеть остаётся снаружи SQLite-транзакций. Общего типа «строка любой таблицы» нет: SQL-проекции описаны отдельно, JSON декодируется на границе. Схема SQLite v1 и формат сохранённых решений сохранены; изменения LLM-протокола имеют отдельную версию промпта.

Стиль закреплён Prettier в `.prettierrc.json`: `bun run format` форматирует TypeScript и конфиги, `bun run format:check` проверяет их без изменений.

`ClassifierPort.classify(snapshot)` возвращает `Effect<Classification, AppError>`. Provider layer создаётся один раз на приложение; `Engine` владеет общим deadline и durable retries. SDK не получает retry-план или handlers инструментов. Для Sonnet 4.5 используется native JSON Schema output; для моделей без него формат reporting tool выбирает SDK, не наш ручной декодер. Протокол отмечен `misaka-evidence-v2`; из safety prompt убрана устаревшая инструкция об обязательном tool call. YAML-политика и выбранная модель не менялись.

Сохранены лимиты evidence и 1024 output tokens, входящий HTTP body ограничен 256 KiB во время чтения. Provider transport изолирован от HTTP layer экспортера OTLP, не следует редиректам и сохраняет отмену при чтении body. SDK-ошибки преобразуются в безопасный `AppError`, `Retry-After` сохраняется. Внутренние SDK spans отключены: сохраняется внешний `moderation.classify`, без raw HTTP context и текстов чатов.

## Поведение

Первое полученное сообщение неизвестного пользователя начинает наблюдение: событие join не обязательно. `clean` **не выдаёт постоянного доверия**. Это намеренное отличие от старой политики: проверок и расходов может быть больше. `/approve` — явное доверие, импортированное доверие помечается `legacy`. `/unapprove` возобновляет проверку новых сообщений.

Bot API и observer сохраняют исходные наблюдения отдельно, но объединяют семантические версии сообщения. Изменения в ту же секунду не теряются только из-за одинакового timestamp. Обрабатываются текст, подписи, entities, кнопки, forwards, доступный reply-контекст и изображения. Observer сохраняет доступные изображения до публикации события; контент адресуется SHA-256. Лимиты — 5 MiB на изображение, 20 MiB/8 изображений на классификацию. Неподдерживаемые или недоступные данные, усечение и повреждённые изображения не позволяют сделать вывод `clean`.

Существующее правило ответа в посторонний канал сохранено в общем классификационном пути: только после успешной проверки linked channel. Неизвестный linked channel — контекст для модели, не автоматический бан. Отправители-каналы и анонимные администраторы архивируются, но не подменяются обычным user ID.

Положительное решение и задание бана записываются одной транзакцией. Бан — `banChatMember(chat_id, user_id)`, без `/sban`, username-поиска и прав на модерацию у observer. Удаление сообщений и уведомление не отменяют подтверждённый бан при собственной ошибке. Новые сообщения при активном решении также получают устойчивые задания удаления.

Незавершённый mutating HTTP после рестарта считается неизвестным исходом, а не гарантированным провалом. Перед новым действием проверяется membership. Чужое или неоднозначное ограничение — `needs_attention`, не присвоение владения и не автоматический unban. Наблюдённые изменения ограничений защищены epoch; Telegram не предоставляет атомарный check-and-mutate, поэтому абсолютно исключить ненаблюдённую внешнюю гонку невозможно.

После подтверждённого бана публикуется короткая ссылка на explain. Уведомления ограничиваются по частоте; их удаление через `FOLLOWUP_TTL_SECONDS` хранится в SQLite. Отмена редактирует видимое уведомление, не убирая TTL. Потерянный ответ отправки восстанавливается только по однозначному собственному сообщению бота, увиденному observer. Без известного message ID гарантировать очистку нельзя; слепой повтор отправки не выполняется.

## Локальный запуск

Из каталога `rewrite/`:

```sh
bun install --frozen-lockfile
cp .env.example .env
# Заполнить BOT_TOKEN, ADMIN_ID, ANTHROPIC_API_KEY и при необходимости список чатов.
bun run start --check-config
bun run start
```

`--check-config` не обращается к Telegram/Anthropic и не создаёт базу. Обычный запуск в **shadow** сохраняет события и классифицирует их, но не исполняет задания модерации. **Shadow расходует Anthropic-кредиты**; диагностические админ-команды могут отвечать в Telegram. Не используйте production-токен одновременно с работающим старым получателем.

Для live нужны одновременно:

```dotenv
MODE=live
ALLOW_LIVE_MODERATION=true
```

Также обязательны либо все три observer-параметра, либо явное `ACKNOWLEDGE_OBSERVER_GAP=true`. Последний вариант принимает неполноту Bot API, а не исправляет её. Боту нужны права ограничения участников и удаления сообщений в каждом чате. Существующий webhook не удаляется автоматически: запуск polling откажется его заменять.

При переходе shadow → live происхождение уже принятых revisions/jobs сохраняется: старый shadow-backlog не становится живыми санкциями. Новые live-события классифицируются в своём режиме. Нельзя переиспользовать одну базу с другим bot ID: идентичность привязана к сохранённому polling offset.

## Observer

```sh
OBSERVER_API_ID=123 OBSERVER_API_HASH=... bun run observer-login --export-session
```

Вход интерактивный; телефон, код и пароль вводятся скрыто. Сессия выводится только явно запрошенным экспортом в stdout, не записывается в репозиторий. Передайте её через секретное хранилище в `OBSERVER_SESSION`, вместе с `OBSERVER_API_ID` и `OBSERVER_API_HASH`. Это полноценный секрет пользовательского аккаунта; read-only — ограничение кода приложения, не Telegram-права сессии.

При запуске проверяется, что сессия принадлежит пользователю, не боту. Потеря связи видна в runtime-логе; runtime повторяет подключение. Полного исторического backfill при разрыве нет. Для удалений basic groups Telegram может не передать chat ID: используется только известное наблюдавшееся соответствие, иначе событие явно отмечается как unscoped, без угадывания.

## Управление

| Команда | Поведение |
|---|---|
| `/approve <user_id>` / reply | Явное доверие участнику этого чата |
| `/unapprove <user_id>` / reply | Снять доверие; проверять новые сообщения |
| `/toggle_bot` | Включить/выключить новые классификации; уже принятые действия не отменяет |
| `/queue_status` | Состояния заданий и действий в разрешённой области |
| `/explain <decision_uuid>` | Сохранённый verdict, статус и допустимое объяснение |
| `/explain <message_id>` / reply | Найти решение по сообщению этого чата |
| `/action <action_uuid>` | Диагностика действия для администратора |
| `/start` | Собственные недавние решения |
| `/start explain_<decision_uuid>` | Explain по deep link |

В группе не раскрывается сырой контекст. В личке участник видит свои причины; администратор целевого чата или настроенный `ADMIN_ID` — подробности и кнопку **«Отменить решение»**. Пересланная ссылка не даёт прав. Отмена идемпотентна, сохраняет исходное решение и создаёт отдельную компенсацию только при доказанном собственном ограничении без более нового/чужого изменения. Удалённые сообщения восстановить нельзя.

## Импорт

Используйте согласованную SQLite-копию, полученную backup API или после остановки старого writer; не копируйте один `.db` во время записи WAL.

```sh
bun run import --source /absolute/legacy.sqlite --target /absolute/new/misaka.sqlite
```

Источник открывается read-only. CLI требует новый target, не сливает существующие базы и не обращается к Telegram. Сохраняются исходные legacy-записи, доверие и настройки чатов; очередь получает импортированное evidence, история verdict — статус `legacy`. Старые claimed bans не превращаются в доказанное владение ограничением и не создают повторных банов. Старые manual approval requests архивируются, старые кнопки `yes` не исполняются. Старый переключатель обязательного ручного согласования не управляет новой автономной политикой.

Внутренний импорт дедуплицируется по таблице/legacy ID; CLI намеренно отказывается перезаписывать target. Импортированное evidence остаётся shadow, поэтому live-запуск не банит всех исторических участников. Актуальные спорные случаи проверяются отдельно.

## Контейнерная сборка и Kubernetes

```sh
docker compose build
docker compose up -d
```

Базовый Bun-образ закреплён по multiarch digest, зависимости — по `bun.lock`. Compose использует непривилегированного пользователя, read-only rootfs, отдельный writable volume `/app/data` и read-only YAML. `.env`, базы и сессии исключены из build context. Для direct Bun и контейнера пути задаются отдельно в `.env.example`.

Зависимости устанавливаются с `--frozen-lockfile --production --ignore-scripts`: используются поставляемые prebuilds/JS-fallbacks, без нативной сборки в slim-образе. Это сохраняет необходимые GramJS зависимости и на Linux/arm64.

### CI и отдельный образ

`.github/workflows/rewrite.yml` запускается на PR, push в `master` при изменении `rewrite/**` или самого workflow, push тега `bun-*`, а также вручную. Сначала Bun 1.4.2 устанавливает frozen dependencies без lifecycle scripts, затем выполняются форматирование, TypeScript и тесты. После этого отдельные native runners собирают и проверяют `linux/amd64` и `linux/arm64`; эмуляция в CI не нужна.

Push в `master` или явный release tag `bun-*` исходного, не fork-репозитория разрешает публикацию в `ghcr.io/<owner>/<repo>-bun`. Два проверенных образа передаются publisher через artifacts, без повторной сборки. После успешных проверок обеих архитектур создаются `sha-<полный commit SHA>-amd64`, `sha-<полный commit SHA>-arm64` и общий multiarch tag `sha-<полный commit SHA>`. Теги `latest`/`master` нового образа не создаются; старый image workflow и его имя не меняются. Registry write token доступен только publisher. PR и `workflow_dispatch` ничего не публикуют.

Для изолированного выпуска используйте тег `bun-<полный commit SHA>` на проверяемом commit и push только этого тега. Он не совпадает с legacy-триггером `v*.*.*`, поэтому не переиздаёт Python-образ и не требует merge в `master`. Это разрешение на публикацию Bun-образа, не на production rollout. Применять образ в инфраструктуре следует по полученному registry digest после успешного publisher.

Воспроизведение проверки из `rewrite/`:

```sh
docker build -t misaka-bun:smoke .
bun run smoke:image misaka-bun:smoke
```

Smoke запускает production-образ без внешней сети (`--network none`), с read-only rootfs и временными writable `/app/data` и `/tmp`; скрипты монтируются read-only, host credentials и базы не передаются. Настоящий CLI работает с локальными Telegram/Anthropic fixtures: `--check-config` без базы/сети, clean → edit → spam без постоянного доверия, shadow-планы без исполнения, SIGTERM, повторный старт без повторной классификации, SQLite integrity и экспорт решений в JSONL. Обязателен non-root UID. Это проверка исполняемого образа, не качества LLM или реальной доставки Telegram.

### Production Kubernetes

Production работает в K3s на `misaka`, namespace `staring-misaka`; Compose выше — локальный способ запуска, не production deployment. Инфраструктура находится в соседнем `misaka.network`: `infras/personal/sites/hetzner/apps/staring-misaka.values.cue`. Текущий Python-процесс использует `/data/telegram_bot.db` на PVC. Новый образ, Secret/env, YAML и writable paths нужно подключать через этот Kubernetes deployment, не запускать рядом второй production Compose.

Безопасная последовательность:

1. Проверить отдельного тестового бота и observer в нужных типах чатов. Проверить доставку чужих bot posts, edits/deletes и права; локальные API-fixtures этого не доказывают.
2. Сравнить shadow-решения и расходы. Не запускать два polling-получателя одного токена.
3. Остановить старого исполнителя в Kubernetes; сделать согласованную финальную копию PVC-базы. Импортировать в свежую отдельную базу, не поверх `/data/telegram_bot.db`. Переключение — с одной репликой и без перекрытия старого/нового poller, не обычный rolling update с surge. Файловая блокировка защищает одну новую базу, не произвольные старые процессы с другой базой.
4. Запустить новый процесс с production-токеном сначала в shadow, проверить приём/observer/права и очередь. Затем включить live с ограниченным `TRACKING_CHAT_IDS`, расширять охват явно. Shadow-окно требует отдельной проверки актуального спама.
5. Для остановки санкций остановить процесс или перезапустить в shadow. Сохранить action ledger и сверить unknown/needs_attention. Не возвращать Python к устаревшей БД: автоматического обратного импорта нет; безопасный rollback — наблюдение и ручная модерация до сверки состояний.

Никакие команды выше не выполнялись против production при реализации.

## Данные и диагностика

- SQLite — источник истины: observations, revisions, snapshots, jobs, decisions, actions, attempts, overrides, commands, audit.
- `JOURNAL_PATH`: транзакционный audit экспортируется в JSONL; ротация 20 MiB × 5, курсор в SQLite. После crash возможна повторная строка с тем же `seq`; потребитель дедуплицирует. Ошибка JSONL не блокирует бан.
- `dirname(DB_PATH)/media/` — сохранённые изображения. В backup входят база и media; одного JSONL недостаточно. SQLite-аудит и media автоматически не очищаются: планируйте место и политику хранения приватных данных.
- `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` — необязательный полный OTLP/HTTP JSON URL, например `http://collector:4318/v1/traces`. Трассы классификации/действий содержат ID, не тексты чатов. Runtime пишет JSON-диагностику в stdout.
- `.process-lock` — материализованная SQLite-база с удерживаемой exclusive-транзакцией; ОС снимает блокировку при crash. Удалять lock-файл у живого процесса нельзя. DB path с hard links отвергается; symlinks канонизируются.

## Проверка

```sh
bun run format:check
bun run check
bun test
```

После перехода на нативный Effect AI прошли 96 тестов и TypeScript; форматирование проверено. Регрессии покрывают конкуренцию и поздние результаты, рестарт последней попытки, unknown outcomes, чужие ограничения, отмену, TTL, observer/Bot API дедупликацию, миграцию чата, shadow/live, импорт, медиа и права explain. Отдельный тест запускает два реальных процесса для блокировки и проверяет освобождение после SIGKILL. Контрактные проверки Effect AI покрывают structured output и reporting-tool формат SDK, token/cache usage, недопустимое evidence, refusal/truncation, HTTP failures без скрытых retries и отмену запроса. Две loopback-регрессии проверяют запрет редиректов и byte limit с включённым OTLP.

Новый CLI smoke с нативным SDK и локальными HTTP fixtures подтвердил: clean → edit → spam без auto-approval; HTTP 401 блокирует задание; 429 сохраняет retry в SQLite и исполняется после рестарта с учётом Retry-After; deadline прерывает чтение body после headers; редирект не выполняется. Выполнены семь локальных model requests, shadow-действия остались без попыток исполнения. OTLP batches не содержали контрольного текста чата, ключа или upstream error body. Платных запросов для этой замены не выполнялось.

Ранее выполнен реальный запуск CLI с loopback Telegram/Anthropic: первое сообщение без join → clean → последующий spam → ban/delete → private explain → undo/unban/обновление уведомления → остановка/перезапуск без повторного бана; JSONL и OTLP экспорт. Импорт CLI проверен на синтетической legacy-базе; Linux/arm64 Docker-образ собран, `--check-config` прошёл без сети, с non-root пользователем и read-only rootfs.
