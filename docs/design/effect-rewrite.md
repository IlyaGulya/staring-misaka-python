# Переписывание Staring Misaka на TypeScript / Effect

Статус: реализация на Bun / Effect 4 находится в [`rewrite/`](../../rewrite/README.md), локальные проверки выполнены; разрешения на production-выкладку нет. Исходное исследование — 2026-09-08. Ниже сохранены архитектурные ориентиры и проверки перед переключением; фактический эксплуатационный контракт описан в README реализации.

## Решение в одном абзаце

Один Bun-процесс в Kubernetes, grammY как адаптер Telegram Bot API, Effect 4 для конкурентности, ошибок и жизненного цикла, SQLite для надёжного состояния и очереди. LLM — официальный Effect AI Anthropic provider за узким `ClassifierPort`, структурированный результат проверяет Effect Schema. Приём обновления, классификация и исполнение бана — разные операции. Вердикт неизменяем; неудачный бан повторяет действие, а не запрос к LLM. Переход с MTProto на Bot API требует отдельной проверки функционального соответствия.

Реализация находится рядом с Python-кодом в `rewrite/`, а не переносит целиком старые ветки. Незакоммиченные Python-исправления сохранены отдельно. Новая state machine закрывает классы ошибок clean/spam, прерванной последней попытки и переиспользования чужого verdict; это не означает исправления старого Python worker.

## 1. Что сохраняем и что уточняем

Сохраняем: несколько отслеживаемых чатов, наблюдение за новичками, явные одобрения, включение/выключение групп, правила и промпты по чатам, структурированный ответ LLM, историю решений, JSONL и OpenTelemetry. Решение пользователя: штатная модерация максимально автономна, без ожидания подтверждения и кнопок ручного повтора. Единственное действие в карточке решения — «Отменить решение». Правила межканальных ответов становятся частью общего механизма принятия решений; отдельного обходного пути бана нет.

После архитектурного разбора выбрана явная политика: неизвестный user наблюдается с первого доступного сообщения, даже без join; чистый verdict не выдаёт постоянного доверия. Явные и legacy-одобрения остаются отдельным состоянием. Это намеренно увеличивает охват относительно старой join-only политики и может увеличить API-расходы. Каналы/анонимные отправители не преобразуются в обычных пользователей.

Решение пользователя: сохраняем юзербота исключительно для наблюдения. Bot API `Update` содержит удаления бизнес-сообщений, но не общее событие удаления сообщений обычной группы, поэтому MTProto-наблюдатель дополняет журнал основного бота. У него собственная сессия; его прикладной интерфейс только публикует наблюдения и не предоставляет отправку команд, бан или удаление. Это ограничение приложения, а не обещание read-only Telegram-сессии. Доступность событий проверяем в каждом типе чата. [Telegram Update](https://core.telegram.org/bots/api#update).

Дополнительные проверки соответствия:

- Команды по `@username`: не обещаем произвольный поиск пользователя. Используем сопоставление пользователей, реально встреченных в чате, проверяем неоднозначность и предпочитаем reply/числовой ID.
- Отправитель-канал и анонимный администратор не превращаются в обычного пользователя: отдельный тип `Actor`, отсутствие ID не означает разрешение банить кого-то другого.
- Переносим текст, подписи к медиа, entities/скрытые ссылки, кнопки, forward/external reply, via_bot и имена. Отсутствующие поля не выдумываем; недоступный внешний контекст не является доказательством спама.
- В конфиге есть обычная TestGroup, не только supergroups: обе категории входят в интеграционные тесты. `migrate_to_chat_id` требует переноса ключей/алиасов группы.
- Для сообщений других ботов проверяем фактическую доставку на тестовой группе: текущие возможности Bot API изменялись. Нельзя опираться на старое обобщение «боты никогда не видят ботов». [Bot FAQ](https://core.telegram.org/bots/faq#what-messages-will-my-bot-get).

## 2. Стек и границы

По прямому выбору пользователя закреплены Bun 1.4.2, `effect 4.0.5`, `@effect/platform-bun 4.0.5`, `grammy 1.46.0` и GramJS `telegram 2.26.22`. Версии находятся в `rewrite/package.json` и `bun.lock`; TypeScript-проверка и Bun-тесты выполнены. Историческая рекомендация Effect 3 больше не является выбранным стеком.

Целевая среда — `oven/bun:1.4.2-slim`; SQLite предоставляет `bun:sqlite`, без better-sqlite3 и отдельной сборки native addon. Docker-образ собран, SQLite persistence/дедупликация/cursor/JSONL проверены внутри Linux-контейнера под uid 1000 с read-only rootfs.

| Модуль | Ответственность |
|---|---|
| `domain.ts` | Типы, port-контракты и типизированная ошибка |
| `telegram.ts`, `telegram-observations.ts` | Bot API transport и отдельная нормализация/извлечение команд |
| `observer.ts`, `observer-observations.ts`, `media.ts` | Read-only MTProto lifecycle, нормализация и устойчивые bounded image blobs |
| `classifier.ts`, `classification/` | `SpamClassifier`: rule, подготовка evidence, Effect AI и доменная проверка результата |
| `store.ts`, `storage/` | Граница транзакций и отдельные workflows ingestion/classification/actions, точные SQL-проекции, импорт и JSONL |
| `commands.ts` | Авторизация, explain, явное доверие и override |
| `engine.ts` | Конкурентность, сетевые действия, таймауты и отмена |
| `telemetry.ts` | Необязательный OTLP exporter |
| `main.ts`, `application.ts`, `runtime/`, `config.ts`, `process-lock.ts` | CLI, сборка runtime, ingress/loops, конфиг, shutdown и единственность исполнителя |

Реальные границы — `Store`, `ClassifierPort` и `TelegramPort`, а не отдельный сервис на каждую таблицу. `ClassifierPort` возвращает типизированный Effect; `TelegramPort` остаётся Promise-границей с AbortSignal. Engine исполняет оба в общем scope отмены. В домен передаются данные, не `grammy.Context`. Синхронная SQLite-транзакция — единственный владелец перехода состояния.

После структурного рефакторинга `Store` не содержит все SQL-переходы в одном классе: он явно задаёт границы транзакций, а workflows разнесены по ответственности. У каждой SQL-проекции свой тип; `ActionPayload`, состояния и диагностические ответы типизированы. Общие Command/Job-типы живут в domain, нормализаторы не импортируют transport ради утилит. Schema v1 и сохранённое поведение не менялись. Стиль закреплён Prettier.

Один Effect runtime на приложение. Effect-программы не запускаются через новый runtime на каждом сообщении. Promise-граница grammY обёрнута с преобразованием ошибок и передачей AbortSignal; отмена HTTP не означает, что сервер не успел выполнить бан. grammY явно требует передавать сигнал через transformers. [Effect runtime](https://effect.website/docs/v3/runtime), [Scope](https://effect.website/docs/v3/resource-management/scope), [grammY transformers](https://grammy.dev/advanced/transformers).

## 3. Приём и сохранение событий

Для текущего VPS выбираем один long-polling receiver через `grammy.Api.getUpdates`, с явным сохранением batch и offset. Не используем одновременно `bot.start`, runner и собственный polling. Сначала транзакция сохраняет сырые updates, inbox-задания и следующий offset; только потом следующий запрос подтверждает batch. При ошибке БД offset не продвигается. Повторная доставка безопасна благодаря `UNIQUE(bot_id, update_id)`.

Это соответствует протоколу: getUpdates подтверждает обновление при запросе с большим offset; Telegram хранит входящие updates не больше 24 часов. `chat_member` надо явно включить в `allowed_updates`. [Bot API](https://core.telegram.org/bots/api#getupdates).

Вместо последовательности без пропусков используем уникальный update_id и локальный ingress_seq: разрывы update_id не являются потерей сообщения сами по себе. Список allowed_updates фиксируется конфигом и покрывается тестом, включая `message`, `edited_message`, `my_chat_member`, `chat_member`, `callback_query`, необходимые channel events. Неизвестные типы сохраняем и диагностируем.

Если позже нужен webhook: отвечаем 2xx только после транзакции inbox, LLM не выполняется в HTTP-обработчике. Секрет webhook проверяется до записи.

### MTProto-наблюдатель

Основной Bot API receiver принимает команды администратора и запускает обработку модерации. Юзербот дополняет аудит: сохраняет доступные ему сообщения, изменения и удаления. Его наблюдения сами по себе не создают второй запрос классификации или действие бана. Сообщение, видимое только юзерботу, явно помечается `observer_only`; покрытие такого случая автоматической модерацией требует отдельной политики, а не молчаливого пропуска под видом полной проверки.

У источников отдельные транспортные ключи и позиции восстановления. В `inbox_updates` уникальность задаётся `(source, source_account, source_event_key)`: MTProto не наследует Bot API update_id/offset. Алгоритм ключей и восстановления MTProto проверяем при выборе клиента. Общая ссылка на сообщение строится из нормализованного peer/chat ID и message ID. Обе исходные записи сохраняются; совпадение сообщения не означает совпадения всех полей или ревизий двух протоколов. Неоднозначную связь удаления с чатом храним как неразрешённое наблюдение, не угадываем chat_id. Поздняя доставка исходного сообщения не должна сбрасывать уже установленный признак удаления.

Падение наблюдателя не останавливает основной Bot API receiver и исполнитель бана: отдельный supervised lifecycle с backoff, метрики подключения/последнего события и явные интервалы неполноты журнала. После переподключения отмечаем результат восстановления; абсолютную полноту событий не обещаем. Удаление остаётся наблюдением факта, а не основанием отменить уже созданный бан.

Целевая граница — `ChatObserver` в том же приложении; конкретная TypeScript MTProto-библиотека пока не выбрана. Если для первого этапа оставляем существующий Python/Telethon, это отдельный процесс с устойчивой локальной доставкой наблюдений и подтверждением после записи основным приложением. Он не пишет напрямую в доменные таблицы SQLite. Такой переходный вариант меняет число процессов и требует отдельной проверки доставки; выбор библиотеки не подменяется предположением, что grammY поддерживает user sessions.

## 4. Состояния, порядок и модель данных

Отдельные сущности — вместо одной очереди «проверить и, может быть, забанить»:

| Таблица | Ключевые поля / ограничения |
|---|---|
| `inbox_updates` | source + source_account + source_event_key UNIQUE, ingress_seq, received_at, raw_json, normalize_status |
| `messages` / `message_revisions` | chat_id + message_id + revision UNIQUE; actor, full text, metadata, observed/deleted state |
| `subjects` | chat_id + actor_id UNIQUE; state, generation, version, evaluated_watermark |
| `classification_jobs` | subject, snapshot_id UNIQUE, state, attempt, next_attempt_at, lease_token, lease_until |
| `decisions` | UUID, immutable input_hash, message revisions, prompt/policy/schema versions, provider/model, verdict/reason, usage, timestamps |
| `moderation_actions` | UUID, subject generation, kind, decision_id, idempotency_key UNIQUE, state, attempts, next_attempt_at, lease |
| `action_attempts` | attempt UUID, action_id, started/completed time, request summary, receipt/error, outcome_unknown |
| `decision_overrides` | decision_id UNIQUE, отменивший admin, время, причина, статус компенсации; исходный вердикт неизменяем |
| `audit_events` | ordered event_id, correlation IDs, event type, payload; transactional with state transitions |
| `notification_outbox` | event_id UNIQUE, delivery attempts, delivered message ID |

Subject states: `untracked`, `monitored`, `ban_pending`, `banned`, `trusted`. Неопределённая классификация оставляет subject под наблюдением, а не создаёт очередь ручного согласования. `needs_attention` — состояние действия, не повод переводить subject в trusted. Явное одобрение и автоматическое одобрение различимы в истории.

Основные инварианты:

1. Положительный вердикт и создание действия сохраняются одной транзакцией. LLM не выполняет инструменты модерации.
2. `ban_pending` никогда не становится `trusted` от обычного чистого сообщения.
3. `banned` выставляется по подтверждённому API-результату или отдельному reconciliation, не по факту создания задания.
4. Повтор действия использует исходный `decision_id`; повторная классификация создаёт новый decision. Старые записи не переписываются.
5. Новые сообщения продолжают приниматься и журналироваться при любом состоянии, включая `ban_pending`.
6. Удаление сообщения не удаляет evidence и не отменяет бан по actor ID.
7. Ошибка, исчерпанная попытка и неизвестный исход имеют явные состояния; ничего не превращается в фиктивный `completed`.

Последовательность обеспечивается на `(chat_id, actor_id)` для решений, административных команд и действий, а разные пользователи обрабатываются параллельно. Внутри процесса допустим keyed scheduler, но право на переход защищено также версией/lease в БД. Для MVP запускается один процесс; второй должен отказать в старте по process lock. Не выдаём локальный Semaphore за распределённую блокировку.

Перед LLM сохраняем неизменяемый snapshot уже принятых сообщений subject. Пока запрос выполняется, ingress продолжает запись. При чистом результате не снимаем наблюдение, если поступили ещё непроверенные сообщения; создаём следующий snapshot. При положительном результате приоритет имеет бан/согласование. Взятие snapshot и проверка watermark при переходе выполняются транзакционно, поэтому быстрое второе сообщение не обходит проверку. Сообщения, доставленные только после завершения периода наблюдения, подчиняются выбранной политике; эффект-система не может предсказать будущую доставку.

На edit создаём revision; изменение текста само по себе не снимает нарушение, зафиксированное в исходной версии. Уже отправленную команду нельзя «отменить» только записью в БД. Отмена решения — отдельный переход и, при необходимости, компенсирующее действие после завершения/reconciliation предыдущего действия того же subject.

### Автономность и отмена решения

Штатный путь: классифицировать → сохранить решение → исполнить → проверить результат. Карточка сообщает о результате постфактум; доставка карточки не блокирует действие. При неоднозначном ответе допускается ограниченная повторная оценка, после исчерпания бюджета сохраняем наблюдение до новых данных. Неопределённость и сбой LLM не означают ни бан, ни доверие. Нет бесконечного цикла повторной оценки одного snapshot.

Для временных сбоев используются сохранённые попытки. После исчерпания короткой серии срабатывает circuit breaker по неисправному сервису/чату: редкие проверки восстановления, ограниченный бюджет и автоматическое возобновление актуальных заданий после успешной проверки. Новые сообщения не перезапускают бюджет неисправного действия. При неизвестном исходе сначала reconciliation; нельзя слепо повторять mutation. Постоянные ошибки требуют исправления причины, но не ежедневного ручного управления очередью. Алерты дедуплицируются по инциденту; восстановление даёт отдельное уведомление.

«Отменить решение» доступно только проверенному администратору и связано с конкретным decision_id. Повторное нажатие идемпотентно. В одной транзакции сохраняем override, запрещаем новые попытки этого решения и создаём компенсацию, если нужна. До отправки бана достаточно отменить задание; при in-flight/unknown сначала устанавливаем итог. Для подтверждённого бана, выполненного нашим решением, компенсация снимает бан. Не снимаем автоматически чужое или более новое независимое ограничение; при неоднозначной принадлежности требуется сверка, а не безусловный unban.

Отмена не стирает аудит, не восстанавливает удалённые сообщения и не означает пожизненного доверия. То же evidence повторно не порождает отменённое решение; новые сообщения могут проверяться. Снятие бана и возврат участника в чат — разные действия, автоматический возврат не обещается. Перед реализацией проверить семантику компенсации выбранного Telegram API и тесты гонок отмены с исполнением.

## 5. Исполнение действий и восстановление

Worker транзакционно получает lease и создаёт attempt, закрывает транзакцию, выполняет HTTP, затем условно фиксирует результат по lease_token/generation. Никаких SQL-транзакций во время LLM/Telegram await. Истечение lease само по себе не останавливает старый HTTP: перед повторным исполнением неизвестного результата требуется reconciliation; старому worker запрещено фиксировать результат с устаревшим token.

При перезапуске не сбрасываем все `processing` в `pending`. Незавершённая попытка становится `outcome_unknown`. Для бана проверяем состояние участника; если ограничение уже действует — записываем подтверждение фактического состояния, не приписывая его обязательно нашей попытке. Если результата установить нельзя — сохраняем неопределённость/needs_attention. Финальная попытка после crash тоже проходит reconciliation, а не зависает за фильтром retry_count.

Бан по числовому user_id. При выборе Bot API учитываем `banChatMember`: в supergroups/channels revoke_messages всегда true. Это отличие поведения от удаления только одного сообщения; его принимаем только после теста и явной фиксации политики очистки. [banChatMember](https://core.telegram.org/bots/api#banchatmember).

Удаление и уведомление — отдельные действия: их сбой не меняет подтверждённый бан. Ключ дедупликации бана включает subject/generation/тип; новые сообщения не создают бесконечно одинаковые баны. Точная однократность внешнего вызова не обещается: транзакции SQLite и Telegram не атомарны. Повтор `sendMessage` при потерянном ответе может дать дубль; алерт содержит стабильный action_id и допускает эту ограниченную неоднозначность.

| Ошибка | Реакция |
|---|---|
| Telegram 429 / provider rate limit | Сохранить время следующей попытки с учётом server retry delay |
| Сеть / 5xx | Ограниченный exponential backoff + jitter; для mutating Telegram — сначала определить, неизвестен ли исход |
| Нет прав / неверная конфигурация | Заблокировать исполнение для затронутой области, один алерт; после подтверждённого восстановления автоматически продолжить актуальные задания |
| Schema decode / refusal / неполный LLM-ответ | Ограниченная отдельная политика; никогда не считать это «не спам» |
| Исчерпание временных ошибок | Circuit breaker, редкие проверки восстановления с бюджетом, автоматическое продолжение актуальных заданий после восстановления |
| Ошибка БД до приёма update | Не подтверждать получение |

Долгий retry живёт в БД, а не в спящем fiber. Встроенные retry SDK и внешние retry worker не перемножаются: один владелец бюджета, выбранный в адаптере. Стартовые предлагаемые лимиты: 3 LLM-запроса, один запрос на subject, таймаут LLM 30 секунд, максимум 3 попытки классификации и 5 попыток временного сбоя действия; уточняем по измерениям, не считаем эти числа свойствами библиотек.

## 6. LLM: контракт и критерии выбора

В реализации используется `effect/ai` из Effect 4.0.5 и официальный `@effect/ai-anthropic@4.0.5`, не старый `@effect/ai` для Effect 3. `LanguageModel.generateObject` формирует запрос и проверяет результат по единственной Effect Schema; ручные envelope/tool JSON Schema удалены. Для текущего Sonnet 4.5 SDK использует native structured output, для моделей без него — reporting tool. Исполняющих tools и agent loop нет. Версии закреплены: AI API помечен `unstable`. Историческое сравнение SDK сохранено в [effect-llm-research.md](effect-llm-research.md).

Domain-результат: `verdict: spam | clean | uncertain`, ограниченная reason, при необходимости evidence_message_ids из переданного snapshot. `uncertain` запускает ограниченную автоматическую переоценку или продолжение наблюдения, не запрос подтверждения администратору. Любой ID, возвращённый моделью, валидируется на принадлежность snapshot; адресат бана берётся только из домена. Не вводим выдуманную «уверенность 0.95» как гарантию качества. Schema проверяет форму, а не истинность вердикта.

YAML-политика и модель сохранены. При переходе на SDK введён `misaka-evidence-v2`: safety prompt больше не требует конкретного tool call. Предыдущий платный replay относится к прежнему протоколу и не доказывает идентичность решений после смены формата ответа. Любые эксперименты с моделью или политикой проводятся отдельно. Текст сообщений и metadata — данные, а не инструкции; классификатор не получает Telegram tools. Большой контекст ограничивается явно; усечение помечается в evidence, а не скрывается.

Provider layer собирается один раз на приложение. Deadline и повторные попытки принадлежат `Engine` и SQLite-очереди; дополнительного SDK retry-плана нет. Максимум ответа — 1024 tokens и 256 KiB HTTP body; потоковый byte limit включается до SDK response lifecycle, чтобы не потерять отмену чтения. `Layer.fresh` изолирует настроенный provider transport от общего FetchHttpClient экспортера OTLP: memoization не должна подменять лимиты и запрет редиректов. Сохраняется безопасный внешний span классификации, внутренние SDK spans с raw HTTP errors не экспортируются.

## 7. Журналирование и эксплуатация

Источником аудита становится `audit_events` в той же транзакции, что и изменение состояния; JSONL — его экспорт, а не единственное свидетельство бана. Exporter хранит позицию, допускает повтор строки при crash с тем же event_id; читатель дедуплицирует. Потеря/переполнение файла видны в метриках и не превращают состоявшийся бан в ошибку модерации.

В каждой записи: event_id, received/occurred timestamps, chat_id, actor_id, message_id/revision, update_id, decision_id, action_id/attempt_id, trace_id, причина перехода. Журнал сообщений сохраняет полный доступный текст/metadata, а trace по умолчанию содержит идентификаторы и размеры без дублирования всего чата. Секреты и URL с bot token в API-ошибках редактируются.

События: received, skipped(reason), classification_started/completed/failed, decision_saved, review_requested/resolved, ban_attempt/confirmed/failed/outcome_unknown, reconciliation, deletion_result, retry_due, needs_attention, manual_override. Для MTProto-наблюдателя сохраняем source; дедупликация сообщений — по chat/message/revision, а транспортные события хранятся отдельно.

Диагностика: команда `/explain <message_id>` в чате/через reply и `/action <id>` в admin-чате показывает цепочку. `/queue_status` различает ожидание, выполнение, retry и needs_attention. Проверяем права для каждого чата при старте и по `my_chat_member`; отказ одного чата блокирует его модерацию, а не скрывается за общим «бот запущен».

Метрики: lag приёма, возраст старейшего задания, ошибки/время LLM, pending bans, outcomes unknown, needs_attention, задержка экспорта. Shutdown останавливает ingress, прекращает выдачу новых работ, ограниченно ждёт текущие HTTP и оставляет незавершённые attempts для восстановления. SQLite — постоянный volume, WAL/busy_timeout, один writer-процесс, резервная копия через SQLite backup API.

### Explain и временное сообщение после бана

Решение пользователя: `/explain` сохраняем. После подтверждённого бана основной бот публикует в исходном чате короткое самостоятельное сообщение: «Участник забанен за спам. Узнать причину — в боте». Ссылка ведёт на `https://t.me/<bot_username>?start=explain_<opaque_token>`. Параметр укладывается в 64 допустимых символа; токен связан с decision_id, не содержит текст сообщения или секреты. Сообщение не зависит от возможности reply на уже удалённый оригинал. [Telegram deep linking](https://core.telegram.org/bots/features#deep-linking).

В личке бот показывает сохранённую причину, время, правило и актуальный статус решения; повторный запрос LLM для объяснения не нужен. Общедоступная часть не раскрывает raw-журнал и чужой контекст. Субъект решения может увидеть своё объяснение, проверенный администратор — подробный аудит и кнопку «Отменить решение». Владение пересланной ссылкой не даёт административных прав. `/explain` по reply или идентификатору использует те же проверки доступа. Для пользователя, открывшего бота без ссылки, предусматриваем поиск его собственных решений по Telegram user_id: после бана он может уже не увидеть follow-up в группе.

Срок жизни follow-up по умолчанию — 1 минута (60 секунд), настраивается по чату. Удаление — устойчивое задание с chat_id, sent_message_id и delete_at в SQLite, а не таймер только в памяти. После перезапуска удаляем просроченные известные сообщения; уже отсутствующее сообщение считаем очищенным. Ошибки прав и истечение допустимого Telegram срока удаления фиксируем отдельно, не повторяем бесконечно. Если сообщение отправлено, но ответ с его ID потерян, используем наблюдения юзербота для сверки там, где связь однозначна; не обещаем гарантированную очистку неизвестного message_id. [Telegram deleteMessage](https://core.telegram.org/bots/api#deletemessage).

Удаление follow-up не удаляет решение и не прекращает доступ к explain в пределах срока хранения. Если решение отменено до отправки уведомления, устаревший follow-up не отправляется; если оно ещё видно, обновляем текст на «Решение отменено», сохраняя срок удаления. Уведомление и его очистка не блокируют бан. При массовом спаме ограничиваем частоту сообщений и объединяем уведомления с отдельными ссылками на решения, чтобы бот сам не засорял чат.

Приёмка: deep link/start и `/explain`, пересланная ссылка без прав, объяснение собственного бана без ссылки, TTL после перезапуска, повтор удаления, потерянный ответ sendMessage, отмена до/после отправки follow-up, ограничение частоты уведомлений.

## 8. Миграция и приёмка

1. Зафиксировать контракты, политику наблюдения и допустимые различия Bot API. Юзербот остаётся наблюдателем; выбрать MTProto-клиент и проверить доставку/восстановление его событий. Собрать минимальный TypeScript spike без переключения продакшена.
2. Перенести чистые правила и нормализацию, построить fixtures из отобранных обезличенных примеров. Исполнять только mock Telegram в replay.
3. Ввести новую SQLite-схему в отдельном файле. Импорт идемпотентный: сохранить UUID/legacy IDs, chat settings, approvals и историю pending reviews. Старые запросы согласования не превращать автоматически в баны: закрыть их как заменённые новой политикой, пометить старые карточки неактуальными и переоценить ещё актуальные случаи с сохранённым evidence. Старый ответ `yes` не исполняет устаревшее решение. Несогласованные legacy-состояния — отдельный отчёт, не произвольный приоритет.
4. Старые BannedUser считать `legacy_claimed_ban`, а не доказанным баном: старая версия писала их до исполнения. Не банить всех этих пользователей заново; актуальные спорные случаи сверять отдельно. Старые claimed/processing/failed задания явно преобразовать и посчитать.
5. Shadow: replay событий/копия нормализованного потока в новую систему с отключёнными mutation actions. Не запускать двух pollers одного Bot API token. Исторический выборочный JSONL не позволяет доказать полноту всех сообщений; фиксируем эту границу. Сравнить решения и причины, отдельно проверить ложноположительные.
6. Cutover: остановить старый исполнитель; сделать согласованную финальную копию SQLite и импортировать в свежую базу; проверить права, новый inbox и единственность процесса; разрешить новую модерацию по одному чату. CLI не выполняет delta-merge в существующий target. Shadow-origin evidence/jobs не превращаются в live-санкции при переключении режима. Смена transport имеет окно неопределённости — сверить перекрывающиеся message IDs и не обещать перенос MTProto offset в Bot API.
7. Rollback сначала останавливает новые mutations и сохраняет action ledger. Нельзя просто запустить старый Python с устаревшей БД: требуется перенос изменений доверия/банов/согласований после cutover и сверка неизвестных исходов. До готовности обратного импорта rollback = режим наблюдения + ручная модерация, а не молчаливый запуск старого исполнителя.

Тесты, обязательные для готовности:

- Исходное сообщение удалено, затем несколько новых → бан всё равно адресован правильному user_id.
- Два одновременных сообщения с разными вердиктами, оба порядка завершения LLM → отсутствие потери бана/снятия наблюдения.
- Crash в каждой границе DB/HTTP, включая последнюю попытку и успех Telegram до фиксации БД → восстановление без зависания.
- Duplicate update/action/admin callback, повторный join, edit, chat migration → предсказуемые идемпотентные переходы.
- Одно сообщение из Bot API и MTProto, разный порядок доставки edit/delete, observer_only и неоднозначное удаление → обе исходные записи в аудите, отсутствие двойной классификации и ошибочной связи с чатом.
- Отключение и восстановление юзербота → основной бот продолжает работу, пробел наблюдения виден, юзербот не исполняет модерацию.
- Нет прав → один алерт и сохранение ban_pending; права возвращены → автоматическое продолжение актуального действия без повторного LLM; circuit breaker ограничивает частоту проверок.
- Отмена до отправки, во время бана и после подтверждения, повторное нажатие, новое независимое решение → корректная компенсация без повторного старого бана и без снятия чужого ограничения.
- Refusal/schema error/timeout LLM → отсутствует автоматическое одобрение.
- Admin override при in-flight ban → последовательность действий и reconciliation, без позднего «старого» бана после unban.
- Файл журнала недоступен, rotation, restart exporter → действия не теряются, event_id позволяет собрать историю.
- Импорт production-копии и повтор импорта → counts/UUID/references совпадают; rollback rehearsal выполнен.
- Реальный Telegram smoke test: обычная группа и supergroup, join/edit, бан/удаление, утрата прав, доставка сообщений ботов, MTProto-наблюдение и восстановление соединения.

Локальные CLI/loopback-проверки покрыли бан, отмену, JSONL/OTLP и восстановление после рестарта, импорт с неизменным источником и отказом изменять существующий target, сборку Linux/arm64-образа и изолированный `--check-config`. Межпроцессная блокировка/SIGKILL входит в тесты; Linux SQLite smoke выполнен ранее. После описанной ниже приёмки прошли 80 тестов, TypeScript и проверка форматирования. Реальные Telegram/MTProto-доставки и исходы санкций этим не доказаны. Полный Python-проект и production пока не заменены.

### Реальный Anthropic replay

37 вручную отобранных случаев, 38 шагов: нормализация Bot API/observer → ingest → claim → настоящий `SpamClassifier` → commit решения. Multi-step случай сохраняет состояние между исходным сообщением и edit. Telegram transport заблокирован, action worker не запускается, API-токен Telegram фиктивный. Недоступные media явно помечены как неполное evidence.

Provider — прямой Anthropic Messages API, модель `claude-sonnet-4-5-20250929`, политика из production YAML. Это целевая регрессионная выборка, не случайная выборка всего трафика и не оценка общей precision/recall.

| Ручная разметка | Шагов | Результат исходного промпта |
|---|---:|---|
| Спам | 21 | 21 spam |
| Нормальные сообщения | 13 | 12 clean, 1 spam |
| Недоступное изображение | 1 | uncertain |
| Спорные, без надёжной разметки | 3 | 1 spam, 2 clean; не оцениваются как правильные |

Первый HTTP 200 выявил ошибку декодера: Anthropic добавляет строки и вложенный объект в `usage`, а старый `Record<string, number>` отвергал весь корректный ответ. Исправлен `classification/anthropic.ts`: обязательные token counters и известные nullable cache counters декодируются отдельно; дополнительные метаданные не мешают verdict. Регрессия воспроизводила отказ до изменения и проходит после него; реальный replay после исправления завершился без ошибок декодирования.

Ложноположительный — `q4300`, профессиональный поиск Android reverse-engineering работы с предложением продолжить в ЛС. Модель расширила правило против сомнительных заработков до профильных услуг. Общее уточнение промпта проверено на этом примере и противоположном случае бытовой подработки: false positive сохранился, спам-контроль остался spam. Неэффективное уточнение **откачено**; нет исключения по конкретной фразе. На одном спорном примере модель также выдумала объяснение «это идиома» — её reason не заменяет ручную разметку.

Всего 40 платных requests, все HTTP 200; первый сохранённый ответ повторно использован без оплаты. Usage: 74 980 input + 4993 output tokens, cache counters нулевые. Расчёт по [тарифу Sonnet 4.5](https://platform.claude.com/docs/en/about-claude/pricing) $3/$15 за миллион — **$0.299835**, не сверка счёта провайдера. Суммарный предварительный резерв $0.984774 при лимите $2. После 40 requests вызовы остановлены; полный повтор корпуса с экспериментальным промптом не выполнялся, в коде сохранён исходный промпт.

### Пропуски и «молочко»

- **Greeting → edit:** в Zenopsis сохранено приветствие и через 10 секунд его замена на предложение сомнительной подработки. В legacy найдены clean-решение и approval после более раннего приветствия, но нет классификации правки. Replay новой версии на свежем subject дал clean → spam; clean не создал постоянного доверия.
- **«Молочко», 8 сентября:** в Zenopsis девять сообщений с обфусцированной подписью; буквальный поиск слова не находил их. Legacy уже классифицировал сообщение `50364` как spam и записал claimed ban в 09:44:41. После записи видны ещё три сообщения. Это **не false negative классификатора**; запись в BannedUser не доказывает успешное исполнение Telegram. Причина отсутствия более ранних сообщений в очереди не установлена.
- В raw Bot API присутствует `guest_bot_caller_user`; часть ответов вызвана reply-командами `/sban` модератора. [Guest mode](https://core.telegram.org/bots/features#guest-mode) позволяет отвечать на mention/reply без членства в чате; [поле caller](https://core.telegram.org/bots/api/types/message.md) описывает инициатора, а не отправителя спама. Нельзя автоматически банить caller: среди инициаторов модератор. Новая версия не использует `/sban`, но replay **не доказывает**, что `banChatMember` остановит guest-ответы. Оба выбранных сообщения «молочка» новая версия распознала как spam по подписи и кнопкам, без видео.

### Импорт и переключение

Настоящий import CLI перенёс все строки восьми legacy-таблиц с побайтово неизменным source; архив сверён поле-в-поле и по legacy IDs. Получено 24 321 уникальное сочетание chat/user и 2378 legacy-решений. Из 5724 queue rows: 5707 completed, 13 failed, 4 claimed; последние 17 доступны для shadow-переоценки. Все импортированные revisions — shadow; **actions = 0**, исторические 14 816 claimed bans не исполняются заново. Integrity checks, повтор внутреннего импорта, стабильность decision IDs и отказ CLI изменять существующий target прошли.

Сохранены 502 legacy approvals. В восьми случаях в том же чате есть и approval, и исторический claimed ban; это не доказательство восьми активных Telegram-банов. У аккаунта из greeting/edit-сценария legacy approval также сохраняется: правило «clean больше не выдаёт доверие» не отзывает уже импортированное доверие. Перед cutover нужен явный пересмотр таких approvals, не молчаливое массовое снятие.

Открытые условия переключения:

1. Разрешить воспроизводимый false positive профильного поиска работы и проверить границы политики; не подменять это исключением по тексту или общей метрикой на 34 успешных шагах.
2. Проверить отдельного тестового бота/observer в настоящих Telegram-чатах: чужие bot posts, guest mode, edits/deletes, права, бан/удаление и восстановление MTProto. Локальный replay этих исходов не проверяет.
3. Согласовать судьбу наследуемых approvals и сверить актуальные спорные ограничения.
4. Выполнить Kubernetes cutover через существующий `misaka.network`, с одной репликой, без одновременного старого/нового polling, финальным SQLite backup и отдельным target. Эта приёмка не меняла инфраструктуру и не выполняла rollout или rollback rehearsal.

## 10. Переход на нативный Effect AI

Выполнен после приёмки из раздела 9. `ClassifierPort` переведён с Promise/AbortSignal на `Effect<Classification, AppError>`; application предоставляет модель через Layers, engine исполняет классификацию непосредственно в своём scope. Старый HTTP envelope decoder и вручную дублированная JSON Schema удалены. Provider-код не знает о санкциях; проверка принадлежности evidence IDs, непустой reason и невозможности clean при неполном evidence осталась в приложении.

Проверки:

- 96 тестов, TypeScript и форматирование проходят. Проверены native JSON output и reporting-tool формат SDK для другой конфигурации модели, cache usage без двойного учёта, недопустимые IDs/reason, refusal/max_tokens/pause, отмена запроса и отсутствие скрытого SDK retry при 401/408/429/503.
- Smoke запустил настоящий CLI с локальными HTTP fixtures и отдельной SQLite-базой: clean → edit → spam; clean не дал approval; HTTP 401 оставил blocked job; HTTP 429 сохранил retry, который завершился после остановки/рестарта с соблюдением Retry-After.
- Прервано реальное чтение HTTP body после получения headers; соединение освобождено. Provider redirect отвергнут. Семь model requests ушли только на loopback; три запланированных shadow actions остались с attempt=0, Telegram mutation methods не вызывались.
- При включённом OTLP получены два trace batch без контрольного текста чата, API key и сырого upstream error body. Smoke выявил переиспользование HTTP layer экспортера вместо настроенного provider transport; оно устранено `Layer.fresh` и защищено двумя постоянными loopback-регрессиями.

Для перехода на SDK не выполнялись платные Anthropic-запросы, production rollout или реальные Telegram-действия. Качество классификации нового протокола `misaka-evidence-v2` требует отдельного сравнения; прежний false positive не объявляется исправленным сменой библиотеки. На момент этого этапа Linux-образ после SDK ещё не пересобирался; последующие сборки и runtime-проверка описаны в разделе 11.

## 11. CI и отдельная линия образов

Добавлен `.github/workflows/rewrite.yml`: Bun 1.4.2, frozen install без lifecycle scripts, форматирование, TypeScript и suite; затем native Linux runners отдельно для amd64 и arm64. База `oven/bun:1.4.2-slim` закреплена по multiarch digest. Проверенные образы передаются publisher через artifacts, повторной сборки перед публикацией нет. Публикация разрешена push в `master` или release tag `bun-*` исходного репозитория: отдельный GHCR package с суффиксом `-bun`, полный SHA в platform tags и multiarch manifest. Изолированный тег `bun-<полный commit SHA>` не запускает legacy workflow с его `v*.*.*` tags и не требует merge в `master`. Ни `latest`, ни legacy tags новый workflow не обновляет; PR/manual runs и forks не публикуют.

`bun run smoke:image <local-image>` запускает настоящий CLI внутри production-образа с `--network none`, non-root, read-only rootfs и tmpfs вместо постоянного data volume. Fixtures, ключи и политика синтетические; ни host `.env`, ни production-база не монтируются. Проверяются config-only без записи, clean → edit → spam, отсутствие auto-approval, планирование shadow без исполнения, graceful shutdown/restart без повторных model calls, SQLite integrity и наличие решений в JSONL. Nullable поля Anthropic fixture проверяются типом SDK, а не второй копией provider schema.

Локально после SDK cutover собраны `linux/arm64` и `linux/amd64` образы; native arm64 smoke прошёл.
